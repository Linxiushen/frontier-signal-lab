The distinct engineering boundary is the separation of active input residency from durable replay evidence. Collected-input source messages can remain in `session_pending_inputs` after consumption. Previously their payloads also entered every hydrated actor's pending-input map. Keeping historical receipts is necessary for replay checks; retaining all their bodies in each actor is a separate resource decision.

## What the pinned sources establish

`hydrateSessionActorState` now adds `consumed_event_id IS NULL` inside the pending-input SQL projection, before serializing those bodies. The actor map and its published metadata therefore omit consumed source rows on hydration. `consumeSessionPendingInput` deletes matching resident entries while the collected-input branch updates durable rows with the aggregate event ID. The ordinary single-input branch still deletes its durable row; this patch does not turn every input into retained history. A stage operation inserts its postimage into the resident map only if its consumed event is null.

A missing resident key no longer proves that an input is new. `readSessionPendingInputByKey` returns an active resident copy when present and otherwise performs the exact session/key SQLite read. Collected-source validation uses the in-memory set only when it contains every required source; otherwise it reads the source set through the existing batched query. The replica preparation path declines a keyed input absent from active residency so the worker can check durable history. These branches retain explicit input IDs, lifecycle generations and original message-byte comparisons. They are source mechanisms and test expectations, not a proof of all replay interleavings.

The actual caller is a serialized physical database execution worker. `captureDurableSessionActor` binds the existing execution admission; `createSessionActorWorker` hydrates a missing/stale resident and stages committed state separately from rollback/invalidation. Its residency implementation already has a 128-session count limit and an 8 MiB ordinary serialized accounting budget, but exempts a sole resident and permits one oversized working set. That budget is therefore not a total process or per-session memory ceiling. This patch reduces one historical-payload component; it does not add bounded admission or backpressure.

## Proposed integration and acceptance boundary

This is a candidate invariant for the existing H2 runtime, without adopting OpenClaw or reopening its closed finite fixtures: active custody and durable replay identity need separate representations. A future intervention must name an actual untested runtime boundary and retain the prior implementation as rollback. Before running it, separately freeze the number of sessions, active versus consumed-history payload distributions, arrival concurrency, pending-byte/admission ceilings and time/resource budgets. This review is not that preregistration.

Acceptance must jointly require exact original receipts and no extra effect on consumed replay, current authority and cancellation, unchanged committed bytes after rollback, bounded terminal drain, and two verified process kills/reopens. Fix the attempted/admitted/completed/refused/replayed/failed members in advance. Compare successful-useful throughput, end-to-end and p95/p99 latency, appropriate process-memory endpoints, SQLite reads/communication and observation cost at matched success rates. Include a retained negative control that treats a resident miss as a fresh input. A small serialized map/reply or logical payload total cannot substitute for peak process memory.
