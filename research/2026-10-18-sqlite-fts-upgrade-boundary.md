The author reports that SQLite 3.54, bundled with Node 26.12, changes how FTS5 `unicode61` handles U+FFFE. An index built with the previous interpretation can then produce a `malformed inverted index` finding even when its source content remains intact. The reported consequence was rejection by Doctor and possible displacement of the whole database by recovery. The native-version reproduction, isolated CLI successes and test counts in the PR body are author reports; we did not execute them. The author explicitly leaves the latest-stable-package upgrade proof unperformed, records a skipped full SQLite inventory, and retains an APFS test timeout.

The selected landed source adds a narrow FTS classification: every non-`ok` finding must match the expected FTS error, and the named virtual table must match a normalized canonical DDL definition. Unknown, drifted or mixed findings do not enter this FTS repair branch. That does **not** mean every unknown recovery case now stays in place: the existing generic corruption path can still move files aside.

Within the existing immediate transaction, the repair owner requests a pre-repair backup before rebuilding only named derived indexes, verifies integrity and foreign keys, and checks current maintenance authority before committing. Recovery first inspects a disposable writable copy with its sidecars, requests all findings, and uses the captured findings for classification. A refused or failed canonical repair returns an issue instead of replacing that source; successful repair is checked again before clearing quarantine. Startup continues to direct the operator to offline Doctor rather than automatically repairing under ordinary admission.

These are source boundaries, not independently established preservation or liveness results. Backup failure can leave temporary or partial backup files. An exhaustive synchronous findings read and rebuild have no independently demonstrated end-to-end deadline. The new portable tests generate a tokenizer mismatch under the current SQLite library and restore the canonical declaration; they do not execute an actual old-package-to-new-package upgrade.

This adds an unexecuted H2 gate. Before releasing one experiment, authenticate adjacent packaged runtimes, record Node/SQLite versions and FTS definitions, and create the indexed data with the actual predecessor runtime. Freeze independent identities and content hashes for sessions, memory and standing intents. Test both Doctor entrypoints, quarantine release and a second restart, alongside unknown/mixed findings, failed backup, lost maintenance authority and interrupted rebuild controls. Preserve the pre-repair snapshot and record DB/WAL/SHM side effects; verify no unauthorized rebuild or replacement after refusal. Require bounded settlement and independent source-row and search-result checks. A missing row, changed identity, unauthorized destructive action or missed deadline falsifies the corresponding preservation claim, even if `integrity_check` says `ok`.

Our earlier [WAL snapshot canary](../results/sqlite-snapshot-canary/report.md) already demonstrates that a structurally valid copy can be stale. This repair adds the other distinction: a derived-index finding need not authorize treating the source database as irrecoverable. Neither observation authenticates a full agent recovery harness.
