# Reject evaluator version drift before committing an outcome

The existing `verifiers_budget_exhaustion.worker` checked frozen files before entering `run_episodes` and again after committing its terminal SQLite outcome. A file change during the runner call therefore raised a version error only after a successful score or a terminal failure receipt had already been persisted. A later selection could still see that completed score. This is a defect in this project's acceptance ordering, not a reproduced Verifiers defect.

The repair moves the existing post-call `verify_files` check before the success/failure branch. The worker still retains the returned episode artifact, but detected drift leaves its allowance reserved with no accepted reward or terminal receipt. Once the prior owner is stopped, ordinary recovery burns that uncertain reservation without granting another entry. Unchanged success and failure outcomes keep their existing behavior. The change adds no observer, dependency or new budget policy.

The actual integration point is the existing native evaluation worker between its `run_episodes` return and `OutcomeBudgetLedger.complete`/`fail`. Long evaluation campaigns amplify the cost of admitting a score with the wrong evaluator version: the durable score can affect selection even if its worker later exits with an error. This repair changes acceptance ordering; it supplies no throughput, latency, resource or quality comparison.

Four portable regressions enter that real project worker and its actual SQLite ledger. Their runner, Echo plugin, configuration type and native import-location check are stubs; they do not execute Verifiers, a scorer or a model. Two controls change a real temporary evaluator file while the stubbed runner executes. On unchanged `fcb9fe8`, both expose the persisted terminal-outcome defect; the two unchanged-file controls pass. With the repair, all four pass, including recovery without replay. Twenty-one neighboring logical/physical-budget and request-identity controls also pass, using stdlib and loopback fixtures only. The initial regression harness stopped at a Windows/Linux path comparison before reaching the target; that diagnostic remains separate from the corrected baseline reproduction.

This is a trusted-owner file-version check, not an atomic filesystem snapshot or a sandbox. A mutation that is restored before the check, or a concurrent change after it, is outside the demonstrated guarantee. Loaded-code identity and arbitrary scoring tampering are not established by these tests. Original frozen protocols/results and failed studies retain their historical evidence; this changed worker must not be substituted into an old freeze. A future native study requires a new exact version binding and separate preregistration. The prior commit remains the rollback path.

No native or scientific experiment ran in this repair. The original H1 negative results, invalid historical RSS and resource gate, H2 finite accepted/failed slices and full H3/H4 unmet gates remain unchanged. The current disk observation is below the existing native resource gate, so no Docker restart, native rerun, model load or resource relaxation was attempted.
