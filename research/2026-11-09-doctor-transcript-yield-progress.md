# Doctor transcript repair: yield boundaries and durable progress

[OpenClaw PR #195459](https://github.com/openclaw/openclaw/pull/195459), authored by `steipete`, merged on 2026-11-09 at 00:15:32 UTC as [56493a1a](https://github.com/openclaw/openclaw/commit/56493a1a999c7f813d13a4431ef8f66fbf22c7c7). The adjacent parent is `a272894e35656b6aa92d9d5dbea2f18a99459726`. This is a review of pinned implementation and test definitions. We did not execute OpenClaw, its tests, a model, or a scientific experiment.

The actual caller is offline `openclaw doctor --fix --non-interactive` during historical transcript inspection and repair. Large compressed histories amplify allocations when a SQLite user-defined decoder executes inside a query predicate. The parent eagerly collects candidate sessions and each session's repair plan. The upstream author reports that decoded values survive within the native statement handle scope even when its predicate returns no rows. Switching to an iterator alone does not address a long sequence of nonmatching rows processed inside one native `next()`.

## Implementation observed

The new SQLite candidate scan projects its predicate as a result column and returns each evaluated physical row to JavaScript. JavaScript collects matching session IDs and applies the resume cursor. The per-session query similarly returns a row with a conditional decoded payload or `null`, allowing the iterator to advance through nonmatches. `kysely-sync.ts` uses a private native SQLite statement, yields iterator rows, and releases its reader and statement in cleanup. Its PostgreSQL branch buffers the result; the new owner therefore preserves PostgreSQL's native filtering and provider `DISTINCT` rather than treating that bridge as a streaming cursor.

`planTranscriptSession` produces batches at 64 rows or 4 MiB of original-plus-rewritten UTF-8 content. It flushes a nonempty batch before adding a row that would exceed the byte threshold. A historical row larger than the threshold is processed alone. These thresholds bound the planned batch; they are not a total process-memory ceiling. A new decoded/repaired row is constructed before that byte check, candidate session IDs remain in a set and sorted array, provider maps are cached for the run, and the provider undo receipt grows with repaired history. This source does not establish constant total memory or a service admission limit.

The writer uses the existing immediate transaction and maintenance-authority assertions for each changed batch. It records provider-restoration row IDs in the same transaction as the rewrite. The existing session cursor advances only on the generator's final `complete` batch, including an empty final batch. If an earlier batch commits and a later batch fails, the session remains eligible for another pass. Already rewritten values no longer require the same restoration, while the unfinished suffix remains reachable. This is a concrete partial-session progress contract; its durability and fault coverage here are source observations, not our executed crash result.

Provider discovery now iterates repeated trajectory facts instead of applying native SQLite `DISTINCT`. Existing logic still accepts one unambiguous provider for the same session/model and leaves unknown or conflicting providers unresolved. The reviewed changed compatibility test deliberately places corrupt compressed bytes in a noncandidate row of a provider-only pass and checks that those bytes are left untouched.

## Test definitions and author measurements

The new batching test injects a write failure at row 64 of 130. It checks that the first 64 provider receipts exist, the session cursor has not advanced, row 64 remains original, and a subsequent migration repairs all rows with one receipt per row. It recreates database access within one test process; it is not two forced process restarts under concurrent arrivals.

The large-corpus test defines a child with a 256 MiB old-space limit, two 4,096-row compressed transcript histories covering nonmatches and candidates, and 4,096 repeated compressed provider facts. It asserts successful migration and exact unchanged compressed payloads plus the intended provider repair. We inspected the definition; we did not observe that test pass or the parent fail locally.

The PR author reports a full Doctor run over 35.19 GiB, 10,800 sessions and 212,274 events completing in 1,148.013 seconds with an unchanged 4,192 MiB heap limit. Reported sampled main peaks are 825.32 MiB overall and 303.41 MiB within the repaired owner. A smaller baseline reportedly OOMed. These are author results, on macOS/APFS and Node 26.12.1, not results reproduced by this project. The reported 20.095 GB cumulative V8 allocation is not retained heap or peak RSS. The committed probe samples every 64 decoder callbacks and at query boundaries, so sampled maxima are not continuous peaks.

The author also reports two A/A controls and five counterbalanced A/B pairs. Owner median wall time changes from 157.934 to 148.898 ms, while whole-command medians change from 30.287 to 32.851 seconds. The author claims no end-to-end speedup. Reported exact payload hashes, stable-upgrade checks and CI are author evidence in the captured PR body; we did not independently download the measurement corpus, run those checks, or verify those CI jobs.

## Engineering decision and limits

This implemented repair supplies useful H2 evidence about a native scan's release boundary and about committing bounded work without advancing durable progress past an unfinished session. It does not validate our Agent runtime's current authority, admission/backpressure, cancellation, effect idempotence or liveness. No dependency is adopted, and an already merged fix is not a new contribution opportunity.

If a distinct integration need is admitted later, freeze the exact runtime/engine, compressed-size and decoded-size distribution, candidate/noncandidate runs, session and provider cardinality, oversized rows, resource ceilings and interruption points first. Acceptance should require the same payloads and receipts, no skipped suffix or duplicated committed effects, cleanup and eventual progress across two actual process restarts, and matched success denominators. Measure useful throughput, end-to-end and tail latency, peak heap/RSS with sampling gaps, storage/communication costs and observer overhead. This is a future criterion, not an executed protocol or a new standalone observer prerequisite.

The review captures all 11 changed head files and three parent contexts, plus the iterator helper; analysis focuses on the production owners, changed recovery/heap/compatibility test definitions and measurement code. The current repository tree response was truncated and is not a complete policy/dependency inventory. The retained receipt lists exact blobs, hashes and scope. H1 negative training results and invalid historical RSS, closed finite H2 slices and its failed concurrent audit, and unmet full H3/H4 gates remain unchanged. There is no local GPU, distributed, production, model-quality or performance result.
