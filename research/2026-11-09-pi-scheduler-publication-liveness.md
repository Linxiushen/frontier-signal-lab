# Pi scheduler: preserve notifications across an awaited planning pass

The landed Pi commit [e50dc7af](https://github.com/earendil-works/pi/commit/e50dc7af97b1a57d72e737b5f066260e2e946ee9), committed on 9 November 2026 at 08:42:28 UTC by Mario Zechner, fixes a concrete liveness boundary in the durable Harness scheduler. This is a pinned source and test-definition review. We did not run its tests or a native workload, adopt the dependency, or change any H1–H4 scientific status.

The actual caller is `TaskScheduler`: a generation can wait for parallel tool tasks, and a completing holder can wait for owned children to end. A publication can notify that scheduler while its current reservation or finalization pass awaits a decision region. The old pass applied cleanup to the same shared pending set after that await. Its stale decision could erase the new notification and leave a task waiting or completing. The commit message and linked [issue 11892](https://github.com/earendil-works/pi/issues/11892) identify this user-visible failure; the implementation diff supplies the mechanism.

The finalization path now copies `#finalizeChecks` and clears that pending set before its first awaited planning call. Checks published during the await remain available to a later pass. The reservation path uses `#planCandidates()`: it takes the old `#runnable` Set, installs a fresh Set before awaiting the plan, and restores surviving old candidates in `finally`. It filters old candidates that were dropped, no longer live, or completing, then merges fresh notifications. A fresh enqueue of the same task ID survives an old plan's decision to drop that ID. This ordering, rather than a new timer or repeated polling, addresses the lost notification.

Two added regression definitions exercise the scheduler through generic task holders and waiters. They use `ControlledStorage`, backed by `MemoryStorage`, to hold publication, intercept `SessionImpl.touch`, and schedule a precise publication with `queueMicrotask` while another pass plans. One expects both holders to become terminal after a child ends; the other expects a waiting task to resume and become terminal after its last dependency is published. These are inspectable tests for two selected in-process interleavings. Reading them establishes neither their execution here nor an actual GenerationTask/tool test, exhaustive concurrency coverage, or restart recovery.

The engineering relevance is tail completion and retained work: with many dependency completions, a lost notification can strand work and prevent idle waits from resolving even when its dependencies have finished. Neither the source diff nor the test definitions measure the incidence of that race, useful throughput, queue growth, latency, memory, or a performance improvement. The temporary Set swap and merge do not establish a workload admission limit or a bound on all scheduler allocations.
