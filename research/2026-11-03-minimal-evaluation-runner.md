`max_concurrent=128` is an active-attempt limit. The runner eagerly creates a Future for every selected slot and gathers all returned episodes. `Env.run_slot` holds a permit through one episode attempt, including finalize, but releases it before retry backoff and before the persistence hook. The queue, retained episode list, total requests, tokens and scoring spend do not acquire durable budgets through this parameter. Large finite tasksets can therefore amplify memory and pending-work costs even with a small active-attempt limit; this is a source inference, not a measured regression or an upstream defect claim.

When a rollout or taskset raises an exception, or another `BaseException` reaches the runner, the runner cancels sibling Futures and awaits them before leaving `serving()`. The new unit-test designs check failure unwind and an iterator that raises after scheduling work. Their `FakeEnv` is not a real remote service. `append_episode` shields both lock acquisition and a background file writer against ordinary cancellation. The writer opens the trace file in append mode and closes it after writing a line; the reviewed path contains no `fsync`. Neither the callback shielding nor the author's tests establish power-loss durability or recovery across process kills.

Both the CLI and direct API refuse an existing nonempty `traces.jsonl`; there is no resume path here. Re-reading a resolved config is permitted only with a fresh or empty output directory; the same finished directory is refused. The author’s successful config-reuse example follows a dry run, which writes no episodes. This is not budget-preserving recovery. A future resumable integration must explicitly retain candidate/attempt identity, spent model and scoring budgets, evaluation version and acceptance membership before it can claim a restart did not buy another attempt.

The terminal summary mixes two stated denominators: successful **episodes**, and mean reward over **all traces**. A multi-agent episode may contribute several traces. `Trace.reward` sums non-None rewards, so this mean does not itself separate scored, skipped, dropped, failed or training-admitted members. Pin the evaluator/rubric/runner versions and retain those memberships before comparing results; the earlier dropped-trace and scoring-policy evidence remains version-specific.

The next integration proposal must name a fixed real taskset and provider/transport, candidate and scoring ceilings, queue/resource caps, failure and cancellation controls, persistence semantics and rollback. It must pre-register applicable success/quality, useful throughput, complete and tail latency, resource/communication and observation costs. This review does not register or run that experiment, replace the unmet Pi/ACP/MCP gate, or reopen any completed H2 slice.
